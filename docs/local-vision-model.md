# Локальная модель зрения для чертежей, планов и схем

Статус: реализован безопасный provider-контракт, demo и опциональный Yytsi adapter; обучение собственной модели отложено. Дата: 26.09.2026.

## Главный вывод

Для проекта нужна не одна «магическая нейросеть», а локальный гибридный конвейер. Геометрию следует извлекать детерминированно из векторного PDF или классическим CV, текст — OCR-моделью, условные обозначения — специализированным детектором/сегментатором, а VLM использовать только для семантической сверки. Ни один результат не должен автоматически становиться подтверждённым планом.

```text
безопасный файл
  → классификация PDF/скан/фото
  → векторное извлечение или нормализация растра
  → OCR и размерные линии
  → стены/двери/зоны/препятствия/оборудование
  → восстановление масштаба и топологии
  → семантическая сверка VLM
  → DraftPlan + confidence + unresolved
  → обязательное подтверждение в 2D-редакторе
```

## Рекомендуемый состав

### 1. Детерминированный слой — источник геометрии

Сначала определить, является ли PDF векторным. Для векторного файла извлекать линии, полилинии, текстовые блоки, размеры и слои напрямую. Для скана использовать OpenCV-подобный конвейер: deskew, бинаризация, удаление шума, линии/контуры, соединение разрывов и построение графа стен.

Этот слой отвечает за координаты. VLM не должна придумывать размеры, масштаб, толщину стены или проходимость.

### 2. OCR и разбор документа

Базовый кандидат — локальный PaddleOCR. Официальная документация описывает PaddleOCR-VL как компактную документную VLM с ядром 0,9 млрд параметров и поддержкой 109 языков, включая русский. Единица: параметр/язык; источник: [официальная документация PaddleOCR-VL](https://github.com/PaddlePaddle/PaddleOCR/blob/main/docs/version3.x/algorithm/PaddleOCR-VL/PaddleOCR-VL.en.md); статус: `source_present`.

Для первой версии лучше использовать OCR только для:

- размерных подписей и единиц;
- названий помещений и зон;
- маркировки дверей, колонн, стеллажей и оборудования;
- основной надписи, номера листа и масштаба;
- легенды условных обозначений.

PaddleOCR-VL уже разделяет layout-анализ и VLM-распознавание, но его штатные классы ориентированы на обычные документы, таблицы и формулы. Поэтому плановые символы и стены требуют собственного детектора, а не только готового document parser. Это согласуется с [официальным описанием двухстадийного pipeline](https://github.com/PaddlePaddle/PaddleOCR/blob/main/docs/version3.x/pipeline_usage/PaddleOCR-VL.en.md).

### 3. Специализированная модель плана

Нужны две небольшие обучаемые головы:

- detector для дверей, ворот, колонн, зарядок, стеллажей, конвейеров, пожарных выходов и условных обозначений;
- segmentation для стен, запретных зон, проездов и рабочих областей.

Архитектура detector может быть RT-DETR-подобной; официальный PP-DocLayoutV2 также использует RT-DETR-L как основу layout detection. Источник: [официальная документация PP-DocLayoutV2](https://github.com/PaddlePaddle/PaddleOCR/blob/main/docs/version3.x/module_usage/layout_analysis.en.md); статус: `source_present`. Но веса нужно дообучать именно на промышленных планах: классы обычного документа не эквивалентны классам чертежа.

### 4. VLM как проверяющий, а не измеритель

Опциональный локальный кандидат — компактный вариант Qwen3-VL. Официальный репозиторий поддерживает локальный запуск и рекомендует vLLM для сервинга. Источник: [Qwen3-VL](https://github.com/QwenLM/Qwen3-VL); статус: `source_present`.

Его задачи:

- связать OCR-текст с ближайшим объектом;
- объяснить легенду;
- предложить тип зоны;
- найти семантическое противоречие;
- вернуть строгое JSON-предложение.

Его запрещено использовать как единственный источник координат, масштаба и факта отсутствия препятствия. Температура для структурированного извлечения — 0. Единица: безразмерная; источник: предлагаемая конфигурация; статус: `assumed`.

## Контракт результата

`LocalVisionProvider.recognize()` должен возвращать `DraftPlan`, а не `Plan`:

```json
{
  "source_sha256": "...",
  "pages": [1],
  "scale": {
    "meters_per_pixel": null,
    "status": "unknown",
    "evidence": [],
    "confidence": 0.0
  },
  "elements": [
    {
      "draft_id": "wall-001",
      "kind": "wall",
      "geometry": {"type": "polyline", "points": []},
      "label": null,
      "confidence": 0.0,
      "source_region": {"page": 1, "bbox_px": [0, 0, 0, 0]},
      "method": "vector|cv|detector|ocr|vlm",
      "status": "needs_review"
    }
  ],
  "unresolved": [],
  "warnings": [],
  "model_versions": {}
}
```

Обязательные свойства:

- координаты источника сохраняются в пикселях, итоговые — в метрах только после подтверждения масштаба;
- `unknown` не заменяется нулём;
- у каждого элемента есть метод, confidence и область происхождения;
- стены и препятствия не считаются проходимыми, пока геометрия не подтверждена;
- пользователь видит overlay «оригинал ↔ распознанный объект» и принимает/исправляет каждый спорный элемент.

## Восстановление масштаба

Порядок доверия:

1. векторные единицы и metadata CAD/PDF;
2. несколько согласованных размерных линий;
3. текстовый масштаб вида `1:100` вместе с размером листа;
4. ручная калибровка двумя точками.

Один текст `1:100` без подтверждения формата листа недостаточен. Если независимые оценки расходятся, масштаб получает `unknown` и симуляция блокируется до ручной калибровки.

Предлагаемый порог расхождения независимых оценок — 2%. Единица: процент; источник: проектная политика `vision-gate-2026.09.1`; статус: `assumed`. Порог должен быть проверен на реальном датасете и версионироваться.

## Данные для обучения и оценки

Минимальные классы разметки:

- wall, door, gate, column, obstacle;
- storage, pickup, dropoff, charger, conveyor;
- route, restricted_zone, emergency_exit;
- dimension_line, dimension_text, room_label, legend_symbol.

Датасет делить по объектам/зданиям, а не случайно по фрагментам одного чертежа, иначе будет утечка. Нужны:

- реальные планы с письменным правом использования;
- синтетические планы, созданные из параметрических шаблонов;
- негативные примеры: таблицы, электрические схемы, генпланы и нерелевантные PDF;
- искажения скана: поворот, перспектива, шум, тени, низкий контраст и разрывы линий.

Метрики:

- OCR: CER/WER отдельно для размеров и названий;
- detector: mAP по каждому классу;
- segmentation: IoU стен и запретных зон;
- геометрия: ошибка масштаба в процентах и координат в метрах;
- топология: связность проходов, число ложных дверей и пересечений стен;
- продуктовая: доля элементов, принятых без правки, и время ручного подтверждения.

Среднее качество нельзя скрывать: публиковать метрики по типу документа, разрешению и объекту.

## Локальное исполнение

Рекомендуемые профили являются инженерной оценкой, а не измерением на текущем стенде:

| Профиль | Состав | Ресурс | Источник | Статус |
|---|---|---:|---|---|
| CPU MVP | vector parser + OpenCV + OCR без VLM | 8–16 ГБ RAM | инженерная оценка | `assumed` |
| GPU OCR | предыдущий слой + PaddleOCR-VL 0.9B | 4–8 ГБ VRAM | инженерная оценка | `assumed` |
| GPU semantic | предыдущий слой + компактный Qwen3-VL | 12–24 ГБ VRAM | инженерная оценка | `assumed` |

Перед выбором профиля провести benchmark на целевом компьютере: 30 типовых страниц. Единица: страница; источник: предлагаемый протокол испытаний; статус: `assumed`.

## Безопасность и отсутствие скрытого поведения

1. Полностью запретить сети процессу inference после предварительной загрузки весов.
2. Хранить веса в `safetensors`, фиксировать SHA-256, лицензию, URL происхождения и SBOM окружения.
3. Не включать `trust_remote_code`; неизвестный Python-код из model repository не исполнять.
4. Запускать worker без root, без Docker socket, без shell и без доступа к `.env`/БД.
5. Принимать только allowlist форматов; проверять MIME по содержимому, а не расширению.
6. Растеризовать PDF в изолированном процессе с timeout, лимитом памяти, страниц и декодированных пикселей.
7. Не поддерживать макросы, вложения, JavaScript PDF и внешние ссылки.
8. Не писать исходные планы и OCR-текст в общие логи; хранить hash, технические метрики и audit event.
9. Каждую версию модели проверять на фиксированном golden set и на canary-наборе вредоносных/аномальных файлов.
10. Никогда не обещать абсолютное «отсутствие бэкдора»: давать проверяемую цепочку происхождения, хеши, сетевую изоляцию и повторяемый аудит.

Предлагаемые входные лимиты до нагрузочного теста:

| Лимит | Значение | Единица | Источник | Статус |
|---|---:|---|---|---|
| размер файла | 25 | МБ | политика безопасности MVP | `assumed` |
| страницы PDF | 50 | страниц/файл | политика безопасности MVP | `assumed` |
| растр страницы | 40 | мегапикселей/страницу | политика безопасности MVP | `assumed` |
| время одного файла | 120 | секунд/файл | политика безопасности MVP | `assumed` |

## Фазы внедрения

### Фаза 0 — уже есть

Ручной 2D-редактор, схема хранения плана, ревизии и детерминированная симуляция.

### Фаза 1 — без обучения

Безопасная загрузка, vector-first parser, OCR размерных линий, ручная калибровка, overlay и `DraftPlan`. Цель — ускорить ввод, не обещая автоматического чертежа.

### Фаза 2 — специализированное CV

Собственный detector/segmentation, golden set, метрики геометрии и топологии, versioned confidence gates.

### Фаза 3 — VLM

Локальная семантическая сверка легенды и зон. Только после измеримого выигрыша над фазой 2 и без передачи файлов наружу.

## Критерий готовности к production

Распознавание можно включить по умолчанию только когда:

- каждый элемент прослеживается до области исходника;
- неверный/неизвестный масштаб блокирует метрические расчёты;
- golden set воспроизводим на чистой машине;
- модель не имеет исходящего сетевого доступа;
- пользователь может исправить и подтвердить результат;
- сохранённый `Plan` создаётся только после подтверждения, а исходный `DraftPlan` остаётся в аудите.

## Реализованный мост к локальному зрению — 26.09.2026

В приложении уже есть безопасный входной слой, `PlanRecognitionProvider`, `DraftPlan`-подобный ответ, provenance/confidence, ревизии и обязательный редактор. Гарантированный demo provider не называется нейросетью.

Первый опциональный adapter — [Yytsi/floorplan-to-3d](https://github.com/Yytsi/floorplan-to-3d): MIT-код, локальный CPU/GPU запуск, SVG-вход и классы floor/wall/door/window. Веса `best.safetensors` загружаются отдельно и должны проверяться по SHA-256. Adapter принимает только loopback HTTP и запрещает redirect.

[xmarva/floorplan-detection](https://github.com/xmarva/floorplan-detection) не включён: в репозитории не обнаружена явная лицензия, а опубликованный способ запуска требует тяжёлого GPU-образа. До юридической и эксплуатационной проверки этот вариант нельзя поставлять в продукте.

Практический следующий baseline: vector-first PDF/SVG → изолированная растеризация → PaddleOCR для размеров/легенд → Yytsi или собственная segmentation head для геометрии → ручное подтверждение. VLM остаётся семантическим проверяющим, а не источником координат или масштаба.
